## ۲. مسیر کامل هر قابلیت (frontend → API → داده)

### ۲.۱ رویدادها و مطالب
- **بررسی اولیهٔ منبع:** صفحه‌های عمومی (`events.html`, `event.html`, `post.html`, خانه) فقط `GET /api/public/site-content` را می‌خوانند که از ردیف یکتای `site_content.id='public'` (یک سند JSON با دسته‌های `events`, `articles`, `partners`, `banners`, …) ساخته می‌شود. تا پیش از این مرحله تنها راه ویرایش، `PATCH /api/owner/site-content` بود که **کل یک دسته** را با `expected_version` جایگزین می‌کرد و برای مدیران بسته بود. مدل موجود کافی بود؛ پس **تغییر ساختاری انجام نشد** و همان سند رکوردبه‌رکورد مدیریت می‌شود.
- **backend** (`backend/content_admin.py`, `site_content.py`, مسیرها در `app.py`):
  - `GET /api/admin/content/{events|articles}?q&status&sort=updated|created|title|date&order&limit≤100&offset` → `{items,total,counts{draft,published,paused,archived},version,source:"site_content",can_edit,can_publish,…}`
  - `GET …/{id}` · `POST …` `{record,expected_version,status?}` · `PUT …/{id}` `{record,expected_version}` · `POST …/{id}/status` `{status,expected_version}` → `{kind,record,version,saved}`؛ `public_path` فقط برای منتشرشده.
  - چرخهٔ وضعیت: `draft → published ⇄ paused → archived → draft`؛ بایگانی حذف نیست. نمای عمومی فقط `published` را برمی‌گرداند (ردیف‌های قدیمی بدون `status` با همان قاعدهٔ قبلی `pub` نگاشت می‌شوند؛ بازگشت‌پذیر).
  - اعتبارسنجی سروری با کد و فیلد: `title_required`, `date_required`, `invalid_jalali_date`, `invalid_image`, `invalid_number`, `invalid_reference`, `invalid_body`, `invalid_date`, `article_body_required`, `event_description_required`, `unexpected_record_fields`, `invalid_status`, `invalid_status_transition`, `status_unchanged`, `content_limit_reached` (422)؛ `site_content_version_conflict` (409)؛ `content_record_not_found` (404).
  - مجوز: خواندن `ev_create` یا `ev_publish`؛ ساخت/ویرایش `ev_create`؛ تغییر وضعیت `ev_publish` (همان ماتریس موجود؛ مجوز تازه‌ای ساخته نشد). نوشتن فقط با CSRF نشست مالک یا مدیر. تاریخچه: `content.create`, `content.update`, `content.status`.
- **frontend** (`admin.js` بخش «مرحلهٔ دوم»، `owner-api.js`): وضعیت و نسخه همیشه از پاسخ سرور نمایش داده می‌شود («رکورد ساخته شد · نسخهٔ ۸ · وضعیت از سرور: پیش‌نویس»)؛ خطای ۴۲۲ زیر همان فیلد؛ تعارض نسخه فهرست را تازه می‌کند و فرم باز می‌ماند؛ هیچ پیام موفقیت پیش از پاسخ سرور نیست.
- **انطباق با سایت عمومی (آزموده روی سرور آزمایشی):** پس از انتشار، `GET /api/public/site-content` رویداد را فهرست کرد؛ پس از توقف ۰ شد؛ پس از انتشار دوباره ۱؛ ویرایش عنوان پس از بازخوانی صفحه و در API عمومی دیده شد؛ مطلب منتشرشده با دو پاراگراف در API عمومی آمد (`logs/flow.log`).

### ۲.۲ فهرست کاربران
- `GET /api/admin/users?q≤80&provider=bale|phone|linked&role=assigned|none&limit≤100&offset` → `{items,total,…,can_open_roles}`؛ ردیف: `account_id, display_name, city, province, role, status, created_at, profile_updated_at, registrations, pending_reviews, providers, bale_user_id, linked`.
- `GET /api/admin/users/{account_id}` → به‌علاوهٔ `registration_items`, `reviews`, `notifications`, `last_session_at`؛ **فقط در نشست مالک** `email` و `manager_username`.
- **هرگز** شماره، digest شماره، هش گذرواژه، توکن یا نشست برنمی‌گردد (آزمون pytest + بررسی زندهٔ کلیدها: `logs/owner-id-tamper.log`).
- مجوز `us_view` در هر درخواست سمت سرور؛ عضو بی‌نقش ۴۰۳، ناشناس ۴۰۱ (`logs/member-negative.log`). شناسهٔ دستکاری‌شده (UUID ناموجود، رشتهٔ غیر UUID، تزریق) فقط `404 user_not_found`.
- پیوند «حساب‌ها و نقش‌ها» از پرونده فقط برای مالک؛ تغییر نقش همچنان فقط از مسیر مالک. **ادغامی با حساب‌ها و نقش‌ها انجام نشد.**

### ۲.۳ حضور و غیاب
- **بررسی اولیه:** ربات دو سازوکار دارد: (الف) جلسه‌بندی و حضور رویدادهای قدیمی در SQLite خود ربات (`attendance_sessions` و وابسته‌ها)؛ (ب) اسکن بلیت فرم‌های سروری با `POST /api/bot/form-tickets/{id}/check-in` که روی پایگاه مشترک می‌نویسد (`ticket_checked_in_at`, `ticket_checked_in_by`). تنها سیگنال مشترک، مورد (ب) است؛ پنل وب فقط روی همان کار می‌کند و (الف) را **نمایش نمی‌دهد و شبیه‌سازی نمی‌کند**.
- `GET /api/admin/attendance/forms?q&limit&offset` · `GET …/forms/{form_id}/people?q&state=checked_in|pending&limit≤200&offset` (ردیف: `response_id, name, mobile_hint, status, payment_approved, ticket_eligible, checked_in, checked_in_at, checked_in_by{kind:bot|web,id}, serial, companion, ticket_type`).
- `POST …/responses/{id}/check-in` `{reason?}` با همان قاعدهٔ ربات: ۴۰۹ `already_checked_in` (جلوگیری از تکرار)، `ticket_payment_not_confirmed` (بدون تأیید پرداخت ثبت نمی‌شود)، `ticket_not_eligible`, `ticket_not_accepted`. `POST …/undo-check-in` `{reason≥3}` → ۴۲۲ `reason_required`، ۴۰۹ `not_checked_in`.
- مجوز `attendance` (موجود در ماتریس)، CSRF، تاریخچه `attendance.check_in` / `attendance.undo_check_in` با دلیل. migration `0027` فقط ستون پوچ‌پذیر `ticket_checked_in_by_account_id` را اضافه می‌کند (عامل وب) و `downgrade` دارد؛ هیچ ردیفی تغییر یا جابه‌جا نشد.
- **سازگاری با ربات:** ستون‌های ربات (`ticket_checked_in_at`, `ticket_checked_in_by`) همان‌هایی‌اند که پنل می‌خواند و می‌نویسد؛ ثبت از پنل با `checked_in_by.kind="web"` و از ربات با `"bot"` تفکیک می‌شود.

### ۲.۴ گواهینامه‌ها و باشگاه (شکاف‌های مستند)
جدول‌های گواهی و باشگاه فقط در SQLite ربات هستند و در پایگاه مشترک همتایی ندارند (`backend/SHARED_DATA.fa.md` به‌روز شد). پیاده‌سازی بدون قاعدهٔ کسب‌وکار (چه کسی گواهی می‌گیرد، امتیاز چگونه محاسبه می‌شود، انتقال شناسه‌های ربات به حساب‌های سرور) به معنی حدس‌زدن منطق بود؛ به دستور، **شکاف به‌جای منطق حدسی ثبت شد**. مسیر پیشنهادی برای مرحلهٔ بعد: اجرای ممیزی روی نسخهٔ پشتیبانِ غیرعملیاتی SQLite ربات (طبق «داده‌ها و مهاجرت» پنل)، تعریف نگاشت `users.bale_id → platform_identities`، و سپس API فقط‌خواندنی گواهی/باشگاه روی پایگاه مشترک.

### ۴.۲ جریان مرورگر واقعی روی سرور آزمایشی (Playwright، Chromium)
`scripts` موقت `_p2_flow.mjs` و `_p2_flow2.mjs` (خروجی در `logs/flow.log`, `logs/flow2.log`)؛ **۰ خطای JS، بدون سرریز افقی** در ۱۲۸۰×۸۰۰ روشن و ۳۹۰×۸۴۴ تاریک/روشن:
- مالک (دسکتاپ روشن): فهرست خالی → ساخت رویداد با تاریخ نامعتبر (۴۲۲ زیر فیلد) → ذخیرهٔ پیش‌نویس (عمومی: ۰) → انتشار بدون شرح رد شد با پیام دقیق → انتشار (عمومی: ۱) → ویرایش عنوان → **بازخوانی صفحه؛ تغییر باقی است** و در API عمومی دیده می‌شود → توقف (عمومی: ۰) → انتشار دوباره (۱) → بایگانی رویداد آزمایشی دوم؛ مطلب با «ذخیره و انتشار» (عمومی با ۲ پاراگراف)؛ کاربران: ۲۱ حساب، جست‌وجو با پیشوند شناسه، پرونده؛ حضور: فرم رایگان → ثبت حضور («حاضر · زمان سرور · از پنل») → برگرداندن با دلیل → ثبت دوباره → **بازخوانی صفحه؛ نمای حضور و وضعیت باقی است** → فیلتر حاضر/ثبت‌نشده → جست‌وجوی سریال؛ تاریخچه ردیف‌های `content.*` و `attendance.*` را نشان می‌دهد.
- مدیر (موبایل تاریک، ورود `staff-login`): ویرایش مکان رویداد (نسخهٔ ۸)، توقف و انتشار دوباره با اثر در API عمومی، فهرست کاربران و پرونده **بدون ایمیل**، ثبت حضور برای «کاربر آزمایشی ممیزی» روی فرم رایگان، تنظیمات قفل.
- یافتهٔ جانبی اصلاح‌شده: عنوان بخش در سرصفحهٔ موبایل کلمه‌به‌کلمه می‌شکست (پیش از این مرحله هم؛ `before/owner-events-mobile-dark.png`) → `admin.css` v103؛ پس از اصلاح `after/33-…`.
- یافتهٔ جانبی اصلاح‌شده: نمای حضور و پروندهٔ سروری کاربر پس از بازخوانی صفحه به فهرست برمی‌گشت → اکنون شناسهٔ فرم/حساب در وضعیت محلی پنل نگه داشته می‌شود (داده همیشه از سرور دوباره خوانده می‌شود).

## ۷. آن‌چه هنوز به سرویس یا تصمیم محصول نیاز دارد
1. گواهینامه‌ها: انتقال/هم‌خوانی `certificates`/`cert_*` ربات با حساب‌های سرور (تصمیم انتقال + ممیزی روی پشتیبان).
2. باشگاه: همان؛ به‌علاوهٔ قواعد امتیاز/سطح که در کد سرور وجود ندارد.
3. حضور رویدادهای قدیمی ربات (`attendance_sessions`): خارج از پایگاه مشترک؛ تصمیم این‌که آیا به فرم‌های سروری مهاجرت می‌کنند.
4. جست‌وجوی کاربران با نام کاربری مدیر (`qa-manager…`) پاسخ نمی‌دهد؛ به‌عمد (نام کاربری اعتبارنامه است و فقط در پروندهٔ مالک نمایش داده می‌شود). اگر لازم شد، تطبیق فقط‌مالک قابل افزودن است.
5. آپلود تصویر رویداد از پنل به انبار فایل سرور (اکنون آدرس همین سایت/https یا دادهٔ تصویری کوچک پذیرفته می‌شود).
