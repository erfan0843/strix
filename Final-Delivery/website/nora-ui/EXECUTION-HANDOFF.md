# بستهٔ شروع فاز اجرایی نورا

**وضعیت مبنا:** ۹ اکتبر ۲۰۲۶ · این برگه بر پایهٔ کد همین checkout است؛ اتصال به سرور یا پایگاه تولیدی را ادعا نمی‌کند.

## خروجی موردنظر

یک وب‌اپ نورا که پنل مالک فقط با نشست واقعی سرور باز شود، داده‌هایش از API مشترک بیاید و فرم‌ساز از تعریف تا ثبت پاسخ مسیر قابل‌آزمون داشته باشد. در توسعه، backend را محلی و ایزوله اجرا می‌کنیم؛ منتظر سرور تولیدی نمی‌مانیم و احراز هویت را هم حذف نمی‌کنیم.

## تصمیم‌های ثابت اجرا

- مسیر سازنده برای کاربر **چهار مرحله** می‌ماند: «مدل و نام»، «فیلدها و تنظیمات»، «مالی و پرداخت»، «مرور و ذخیرهٔ پیش‌نویس». شش فاز زیر ترتیب توسعه‌اند، نه شش قدم تازه در رابط.
- وب‌اپ مستقل است؛ ورود مدیر وب با نام کاربری و گذرواژهٔ سروری روشن می‌ماند و محصول Bale-only معرفی نمی‌شود.
- نقش و مجوز مرجع سروری دارند. نشست یا نقش نمونهٔ مرورگر، مسیر جایگزین ورود مالک نیست.
- کیفیت‌سنجی آفلاین است؛ پاسخ برای تحلیل به سرویس بیرونی نمی‌رود و دانشگاه/فهرست محلی حذف نمی‌شود.
- پیش‌نمایش فرم، دادهٔ واقعی را خودکار پر نمی‌کند و ثبت‌نام، پرداخت یا پیام واقعی نمی‌سازد. اتصال بیرونی تا تأیید صریح و آزمون staging خاموش می‌ماند.
- قابلیت‌های نمونه‌ای پنل به‌عنوان دادهٔ واقعی عرضه نمی‌شوند؛ fixture فقط در آزمون صریح فعال است. در تولید، بخش فاقد API باید خالی/غیرفعال و با محدودیت روشن باشد؛ هیچ نمونه‌ای جای دادهٔ سرور نمی‌آید.

## وضعیت آخرین بازبینی — ۹ اکتبر ۲۰۲۶

- ورود پنل مالک/مدیر پیش از نمایش داده، از API و نقش سروری عبور می‌کند؛ ورود محلی و نقش آزمایشی در تولید fallback نیست.
- محتوای عمومی سایت از snapshot سرور می‌آید؛ رویداد/مطلبی که API برنگرداند در سایت نمایش داده نمی‌شود. صفحهٔ رویداد و مطلب و پیوندهایشان آزمون شده‌اند.
- فرم‌ساز چهاره‌مرحله‌ای، مسیر پاسخ سروری، کارتابل پشتیبانی‌شده، گزارش تجمیعی و مدیریت نقش‌های سروری آزمون دارند. ارسال عمومی و پرداخت واقعی در آزمون فعال نشده‌اند.
- بات به API مشترک برای هویت، فرم‌ها، پرونده/رسیدهای پشتیبانی‌شده، فایل‌ها و اعلان‌ها وصل است؛ ماژول‌های قدیمی رویداد/پرداخت/حضور/گواهی/مالی هنوز کامل منتقل نشده‌اند و گزارش فاقد API نباید از SQLite پر شود.
- آزمون‌های آخر این checkout: ۱۴ فایل Node (۱۳ فایل رابط/سرور + آزمون فونت)، ۹۹ آزمون backend و ۱۰۸ آزمون تابع‌محور بات موفق‌اند. آزمون‌های اجرایی قدیمی بات عمداً از collection خودکار pytest کنار گذاشته شده‌اند.
- PostgreSQL عملیاتی، secretهای واقعی، میزبانی staging و اتصال زندهٔ بله در این محیط پیکربندی یا تأیید نشده‌اند؛ نتیجهٔ آزمون محلی به‌معنی آماده‌بودن استقرار نیست.

## خط مبنا: چه چیزی در کد هست

| لایه | وضعیت قابل مشاهده در checkout |
|---|---|
| رابط | صفحات وب، سازنده، فرم پاسخ، ورود و `admin.html` موجودند. `admin.js` ابتدا نشست سرور را بررسی می‌کند. |
| backend واقعی | `docs/fa/nora-ui/backend/app.py` یک برنامهٔ FastAPI هم‌مبدأ است؛ مسیر ورود مالک/مدیر، نقش سروری، فهرست/ذخیرهٔ پیش‌نویس، انتشار مالک‌محور، پاسخ فرم، گزارش تجمیعی و چند workflow پیاده شده‌اند. آزمون‌های API با SQLite موقت موجودند. |
| پنل مالک | ورود و نقش از API سرور است؛ داشبورد، گزارش‌های پشتیبانی‌شده، کارتابل و فرم‌ها از API می‌آیند. رویداد/مطلب و زیربخش‌های فاقد endpoint در تولید دادهٔ نمونه نشان نمی‌دهند و با وضعیت خالی/محدودیت مشخص می‌شوند. «ورود واقعی» به‌تنهایی قابلیت فاقد API را عملیاتی نمی‌کند. |
| سرور Node | `server.mjs` فقط فایل‌های استاتیک و scaffold محدود را ارائه می‌کند؛ جای FastAPI نیست. بازکردن آن به‌تنهایی API مالک را اجرا نمی‌کند. |
| استقرار | اتصال PostgreSQL، secretهای محیط اجرا و آزمون روی میزبان staging در این checkout اثبات نشده‌اند. آزمون محلی معادل آمادگی تولید نیست. |
| قرارداد فیلدها | `forms-field-audit.md` اختلاف کاتالوگ تاریخی ۷۸تایی و کاتالوگ وب فعلی را ثبت کرده؛ نباید بی‌تصمیم هر ۷۸ مورد را قابلیت زنده فرض کرد. |

## نقشهٔ شش‌فازی اجرای کار

این نقشه ترتیب توسعه را برای همین checkout مرتب می‌کند؛ مسیر کاربر در سازنده همان چهار مرحلهٔ ثابت بالاست.

### فاز ۱ — محیط توسعهٔ واقعی و قابل تکرار

**کار:** FastAPI را با پایگاه جدا از production اجرا کن؛ migrationها، health و ورود عادی مالک را از همان origin وب بررسی کن. برای کار محلی می‌توان از SQLite جدا استفاده کرد؛ برای staging/production مقصد PostgreSQL است. مالک توسعه از متغیرهای محیطی محلی ساخته می‌شود، نه از نقش hardcodeشده در رابط.

**خروجی:** دستور راه‌اندازی تکرارپذیر، health سبز پس از migration، صفحهٔ ورود وب، نشست مالک واقعیِ همان DB محلی، خروج/ابطال نشست و CSRF سالم. `server.mjs` به‌عنوان backend جا زده نمی‌شود؛ secret در Git/HTML/localStorage ثبت نمی‌شود.

**معیار عبور:** `GET /api/health` حالت `same-application` و اجزای واقعاً آماده را نشان دهد؛ ورود از مسیر وب به `/api/auth/me` مالک برسد؛ ورود نامعتبر/نشست منقضی رد شود؛ هیچ تحویل بیرونی فعال نباشد.

### فاز ۲ — بستن قرارداد محصول و داده

**کار:** قرارداد v1 را از schema و capabilityهای سرور استخراج کن: مدل‌های فرم، فیلدهای واقعاً پشتیبانی‌شده، اعتبارسنجی، شرط نمایش، نقش‌ها، وضعیت draft/published و نگاشت داده. اختلاف تاریخی ۷۸ نوع در برابر فهرست UI جداگانه ثبت می‌شود؛ نوعی که قرارداد و آزمون ندارد منتشرشدنی معرفی نمی‌شود.

**خروجی:** ماتریس واحد «قابلیت × رابط × API × مجوز × آزمون» و فهرست روشن موارد پشتیبانی‌نشده.

**معیار عبور:** پاسخ هر کنترل رابط با schema/API همان رفتار را داشته باشد؛ هیچ قابلیت حساس فقط با پنهان‌کردن دکمه مجاز/غیرمجاز نشود.

### فاز ۳ — سازنده و پیش‌نویس چهارمرحله‌ای

**کار:** مسیر چهارمرحله‌ای موجود را به draft API، نسخه‌بندی و readiness وصل کن؛ ذخیره و بازیابی بین نشست‌ها را با نشست مالک/مدیر مجاز امتحان کن. مبلغ و روش پرداخت فقط به‌صورت تنظیم امن و fail-closed نمایش داده شوند؛ انتشار مالی تا اتصال و پذیرش سرور فعال نشود.

**خروجی:** ساخت، ویرایش، بازیابی، اعتبارسنجی و ذخیرهٔ draft از هر مرورگر مجاز؛ تعارض نسخه با پیام قابل‌اقدام؛ preview جدا از دادهٔ پاسخ.

**معیار عبور:** draft جدید پیش‌نویس می‌ماند؛ ویرایش هم‌زمان داده را بی‌صدا بازنویسی نمی‌کند؛ خطای API به موفقیت محلی تعبیر نمی‌شود؛ wizard همچنان چهار مرحله دارد.

### فاز ۴ — پاسخ عمومی و پروندهٔ شخص

**کار:** مسیر پاسخ منتشرشده را از مرورگر تا backend و DB با دادهٔ ساختگی آزمون کن. سیاست رضایت و نگاشت هر فیلد به پروندهٔ شخص باید صریح باشد؛ هیچ مقدار پروفایلی در فرم خودکار وارد نشود. تکمیل پرونده پس از پاسخ، اگر مجاز باشد، باید سروری، قابل‌ردیابی و هم‌راستا با قواعد مالکیت باشد.

**خروجی:** ثبت/بازیابی امن پاسخ، اعتبارسنجی مجدد سمت سرور، صفحه‌بندی و دسترسی محدود مدیر؛ پاسخ‌های شخصی در تحلیل/گزارش عمومی افشا نشوند.

**معیار عبور:** پاسخ ناشناس بدون حساب قابل ثبت باشد؛ دسترسی غیرمجاز/تکرار/تغییر نسخه رد شود؛ آزمون‌ها دادهٔ واقعی و سرویس بیرونی مصرف نکنند.

### فاز ۵ — پنل مالکِ داده‌محور

**کار:** هر بخش پنل را جداگانه به endpoint موجود وصل کن و آزمون نقش بگذار. endpoint گزارش `GET /api/admin/reports/summary`، فرم‌های سروری، فهرست نقش‌ها، کارتابل و انتشار snapshot محتوا آزمون دارند. برای هر قابلیتِ بدون endpoint، عملیات را غیرفعال و empty state شفاف نشان بده؛ fixture محلی در تولید—even با برچسب—جایگزین دادهٔ سرور نمی‌شود و آمارها با هم ادغام نمی‌شوند.

**خروجی:** داشبورد مالک فقط آمار پاسخ API را نشان می‌دهد؛ مدیر/سرپرست فقط مجوز سروری خودش را می‌بیند؛ عملیات مالک با نشست، CSRF و نسخهٔ مورد انتظار انجام می‌شود.

**معیار عبور:** آزمون مالک/مدیر/عضو برای هر endpoint؛ نبود داده یا خطای API با عدد نمونه جایگزین نمی‌شود؛ نقش مرورگر هرگز مجوز سرور نمی‌سازد.

### فاز ۶ — staging، پذیرش و عرضه

**کار:** روی hostname و PostgreSQL جدا، migration/rollback، TLS، cookie امن، origin/CSRF، rate limit، backup/restore، دسترس‌پذیری صفحه‌کلید/صفحه‌خوان و موبایل را بررسی کن. برای ربات فقط دامنه‌های مشترک تأییدشده را مرحله‌ای متصل کن؛ انتقال DB قدیمی بدون طرح تطبیق، backup و گزارش تعارض انجام نشود.

**خروجی:** گزارش پذیرش تاریخ‌دار شامل commit، نسخهٔ schema، نتیجهٔ هر سناریو و محدودیت‌های شناخته‌شده؛ رازها و دادهٔ شخصی در گزارش نباشند.

**معیار عبور:** فقط پس از پذیرش صریح مالک، قابلیت‌های بیرونیِ جداگانه (OTP واقعی، اعلان، پرداخت، پیام‌رسان) برای staging/production پیکربندی شوند. نتیجهٔ JSDOM/SQLite به‌تنهایی مجوز عرضه نیست.

## صف اجرای فوری

1. **E1 — راه‌اندازی FastAPI محلی، نه Node scaffold:** پیروی از `backend/README.fa.md`؛ محیط مجازی، DB توسعهٔ جدا، migration، تنظیم مالک توسعه در محیط محلی و بررسی health/ورود. گذرواژه را با اسکریپت همان README هش کن و در چت یا repo ننویس.
2. **E2 — خط مبنای آزمون:** اجرای تست‌های کامل backend و smoke وب؛ خطاها را قبل از افزودن قابلیت تازه دسته‌بندی کن.
3. **E3 — گزارش و داشبورد سروری (آزموده):** `loadServerReports()` و کارت‌های پشتیبانی‌شده از API مشترک تغذیه می‌شوند؛ شکست یا نبود endpoint دادهٔ محلی/نمونه را جایگزین نمی‌کند. پذیرش زندهٔ staging هنوز لازم است.
4. **E4 — برش عمودی فرم:** مرور چهار قدم، ساخت draft، بازیابی، readiness و انتشار فقط با مالک؛ بدون ارسال بیرونی/پرداخت.
5. **E5 — پذیرش نقش:** همان مسیر را با مدیر، سرپرست و عضو اجرا کن؛ رد دسترسی باید از backend بیاید، نه از UI.

## فرمان‌های مرجع موجود در پروژه

از ریشهٔ مخزن. نمونهٔ محلی زیر یک DB جدا می‌سازد و همان احراز هویت سروری را نگه می‌دارد؛ برای production/staging از آن استفاده نکن. مالک توسعه را از متغیرهای محیطی بساز و `NORA_OWNER_PASSWORD_HASH` را با فرمان تعاملیِ امنِ `backend/README.fa.md` تنظیم کن؛ رمز خام را در فایل یا چت نگذار. `NORA_COOKIE_SECURE=0` فقط برای HTTP محلی است؛ روی HTTPS مقدار `1` بماند.

```bash
export NORA_DATABASE_URL='sqlite:////tmp/nora-dev.sqlite3'
export NORA_OWNER_ID='local-dev-owner'
export NORA_OWNER_USERNAME='nora-dev-owner'
export NORA_COOKIE_SECURE=0
# NORA_OWNER_PASSWORD_HASH را با scrypt hash تعاملیِ README تنظیم کن.

python3 -m venv .venv
.venv/bin/python -m pip install -r docs/fa/nora-ui/backend/requirements.txt
.venv/bin/python -m pip install -r docs/fa/nora-ui/backend/requirements-dev.txt
.venv/bin/alembic -c docs/fa/nora-ui/backend/alembic.ini upgrade head
.venv/bin/uvicorn --app-dir docs/fa/nora-ui backend.app:app --host 0.0.0.0 --port 8000
```

برای اولین اجرای واقعی UI/API، به‌جای `node server.mjs` از FastAPI استفاده کن. برای جزئیات نام متغیرها، ساخت hash گذرواژه و مرز سرویس‌ها، مرجع اجرایی `backend/README.fa.md` است. DB محلی را با staging/production مشترک نکن.

آزمون‌های اصلی:

```bash
PYTHONPATH=docs/fa/nora-ui .venv/bin/python -m pytest -q docs/fa/nora-ui/backend/tests
NODE_OPTIONS=--max-old-space-size=3072 node docs/fa/nora-ui/smoke.test.mjs
node docs/fa/nora-ui/login.test.mjs
node docs/fa/nora-ui/admin-rbac.test.mjs
node docs/fa/nora-ui/server.test.mjs
```

## راستی‌آزمایی خط مبنا

در همین نوبت و پس از کنارگذاشتن پیش‌نمایش موقت پنل، این آزمون‌های آفلاین اجرا شدند:

- smoke وب: **۷۵۸ قبول، ۰ خطا**.
- backend: **۹۹ قبول، ۰ خطا**؛ یک هشدار deprecation از `starlette.testclient`.
- ورود وب: **۷۹ قبول، ۰ خطا**.
- RBAC پنل و آزمون‌های server scaffold: موفق؛ آزمون server شامل **۶ مورد** است.

این نتیجه فقط صحت مسیرهای آزمون‌شده در محیط محلی را نشان می‌دهد؛ PostgreSQL/staging و استقرار واقعی هنوز آزموده نشده‌اند.

## دروازهٔ شروع

**می‌توان فاز ۱ را همین حالا با backend محلی آغاز کرد؛ سرور تولیدی لازم نیست.** چیزی که هنوز نمی‌توان ادعا کرد: پنل کاملِ داده‌محور، staging/PostgreSQL پذیرفته‌شده یا آماده‌بودن عرضه. تحویل بعدی باید یک vertical slice واقعی و آزموده باشد، نه صفحهٔ ورود تنها و نه preview محلی با نقش ساختگی.
