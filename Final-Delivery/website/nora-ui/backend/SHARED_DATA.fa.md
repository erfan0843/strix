# دادهٔ مشترک وب‌اپ و ربات

## مبنای اجرایی

در این پیاده‌سازی، PostgreSQL متصل به FastAPI منبع اصلیِ مسیرهای مشترک است. API و کلاینت بات برای هویت و نقش، کارتابل بررسی پروفایل و فیش، اعلان‌های حساب، پیوست خصوصی و تحویل فایل از بات پیاده شده‌اند؛ گزارش‌های گفتگویی بات و پنل وب نیز برای داده‌های موجود فقط جمع‌های مجاز را از همان API می‌خوانند. API محتوای منتشرشده را نیز بدون بایت فایل در خروجی عمومی ارائه می‌کند. migrationها افزایشی‌اند و هیچ دادهٔ قدیمی را منتقل، بازنویسی یا حذف نمی‌کنند.

کد ربات در `bale-bot/nora_bot/` و UI/backend در `website/nora-ui/` جداست؛ وابستگی‌های نصب نیز جدا هستند (`bale-bot/nora_bot/requirements.txt` و `backend/requirements.txt`). صفحهٔ ورود عضو از OTP شماره با Safir استفاده می‌کند؛ مالک و مدیران یک فرم مشترک نام‌کاربری/گذرواژه دارند و `/api/auth/staff-login` هویت را با تنظیمات مالک یا اعتبارنامهٔ مدیرِ واگذارشده تطبیق می‌دهد. endpointهای اختصاصی `/api/auth/login` و `/api/auth/manager-login` نیز در backend باقی‌اند. endpoint امضای `initData` بله (`POST /api/auth/bale-mini-app`) در پوستهٔ مشترک (`ui.js`) مصرف می‌شود: اگر صفحه داخل شیشهٔ مینی‌اپ بله باز شود و `Bale.WebApp.initData` معتبر باشد، پوسته نخست وضعیت نشست را می‌پرسد و تنها در نبود نشست، امضا را یک‌بار به سرور می‌دهد. صفحهٔ ورود وب (شماره/گذرواژه) دست‌نخورده می‌ماند و جایگزین آن نیست. نقش حساب از پایگاه‌داده می‌آید و فقط مالک آن را تعیین می‌کند؛ OTP به‌تنهایی نه نقش می‌سازد و نه مجوز مدیریتی وب می‌دهد. ربات پیش از شروع باید API مشترک و هویت سروری را بررسی کند؛ پس از آن، بخش‌های قدیمیِ منتقل‌نشده هنوز از SQLite ربات استفاده می‌کنند. بنابراین اتصال مسیرهای این فاز آمادهٔ اجراست، اما مهاجرت همهٔ حوزه‌های قدیمی و راه‌اندازی عملیاتی پایگاه تولیدی هنوز کامل نشده‌اند.

## هویت مشترک

- `accounts` شناسهٔ داخلی و پایدار حساب است.
- `platform_identities` شناسهٔ هر سکو را به یک حساب وصل می‌کند؛ شناسهٔ بله و digest پایدار شمارهٔ OTP یکتا هستند و شمارهٔ خام در challenge/شناسهٔ OTP ذخیره نمی‌شود.
- مسیر `POST /api/auth/bale-mini-app` دادهٔ خام را با توکن فقط‌سروری `NORA_BALE_BOT_TOKEN` می‌سنجد، تاریخ را کنترل می‌کند، اثرانگشت ورود تکراری را رد می‌کند و نشست قابل ابطال می‌سازد. `get_or_create_bale_account` فقط نگاشت هویت را انجام می‌دهد.
- مسیرهای `POST /api/auth/phone-otp/request` و `verify` کد را با پیامک از راه Safir تحویل می‌دهند و بعد از کد معتبر نشست provider=`phone` می‌سازند؛ این مسیر به حساب یا Mini App بله متکی نیست. شماره و کد در DB فقط به‌شکل HMAC نگه‌داری می‌شوند. Safir برای OTP احراز هویت است و صف پیام/اعلان عمومی از آن استفاده نمی‌کند. `POST /api/auth/bale-mini-app` برای کلاینت‌های یکپارچه باقی است، اما در صفحهٔ ورود وب ارائه نمی‌شود.
- مدیر فقط وقتی وارد پنل وب می‌شود که مالک برای حسابِ ازپیش‌نقش‌گرفته اعتبارنامهٔ مدیر تعیین کرده باشد؛ فرم مشترک با `/api/auth/staff-login` و endpoint اختصاصی `/api/auth/manager-login` نشست provider=`manager-password` می‌سازند و `/api/account/me` نقش جاری را از DB می‌خواند. APIهای مدیریتی وب نشست مالک یا provider=`manager-password` می‌خواهند؛ نشست OTP به‌تنهایی مجوز وب نمی‌دهد. برای نقش معتبر در بات، حساب همچنان به شناسهٔ بله نیاز دارد. نشست مالک و مسیرهای مالک‌محور نیز جدا هستند.
- مستند رسمی بله، `Bale.WebApp.initData` را رشتهٔ خام URL-encoded می‌داند و اعتبارسنجی را با مرتب‌سازی فیلدها، ساخت رشتهٔ جداشده با خط جدید، HMAC-SHA-256 با کلید `WebAppData` و بررسی `hash` شرح می‌دهد. زمان `auth_date` نیز باید برای جلوگیری از پذیرش دادهٔ کهنه بررسی شود: <https://docs.bale.ai/miniapp>.
- نقش‌های سروری فقط `owner`، `manager` و `club-supervisor` هستند. مالک از نشست مالک شناخته می‌شود؛ مالک می‌تواند حساب تأییدشدهٔ بله یا OTP را مدیر/سرپرست باشگاه کند یا نقش را بردارد. مدیر مجوزهای عمومی را دارد و به مدیریت باشگاه دسترسی ندارد؛ سرپرست مجوزهای مدیر و چهار مجوز روشن باشگاه را می‌گیرد. `cl_dues` و `sys_points` فعلاً به نقش‌های غیرمالک واگذار نمی‌شوند.

## برخورد طرح‌های داده

جدول‌های `forms`، `form_fields` و `form_responses` در ربات SQLite و API نام یکسان اما شناسه‌ها، ستون‌ها و چرخهٔ کاری متفاوت دارند. اتصال مستقیم یا تغییر نام خودکار امن نیست. جدول `users` ربات نیز همتای حساب‌محور در API ندارد؛ تطبیق بر پایهٔ نام، شماره یا کد ملی انجام نخواهد شد.

انتقال داده در گام‌های بعدی باید از نسخهٔ پشتیبانِ دست‌نخورده آغاز شود: اجرای آزمایشی روی پایگاه جدا، گزارش شمار رکوردها و تعارض‌ها، تطبیق کلیدها و روابط، بررسی نمونه‌ها، سپس انتقال کنترل‌شده با امکان بازگشت. فایل SQLite اصلی تا تأیید نتیجه محفوظ می‌ماند.

## محتوای عمومی، فهرست کاربران و حضور در پنل وب (مرحلهٔ دوم پنل)

- **رویدادها و مطالب** تنها یک منبع دارند: سند JSON ردیف `site_content.id='public'` که `GET /api/public/site-content` و صفحه‌های عمومی همان را می‌خوانند. مسیرهای `/api/admin/content/{events|articles}` روی همان سند، رکورد‌به‌رکورد کار می‌کنند (ساخت، ویرایش، تغییر وضعیت با `expected_version`). وضعیت رکورد `draft → published ⇄ paused → archived → draft` است؛ بایگانی حذف نیست و نمای عمومی فقط `published` را نشان می‌دهد. هیچ جدول یا انباشت موازی برای رویداد ساخته نشده است.
- **فهرست کاربران** (`/api/admin/users`) از همان جدول‌های `accounts`، `platform_identities`، `account_profiles`، `form_responses` و `admin_tasks` خوانده می‌شود و برای مجوز `us_view` است. این فهرست با «حساب‌ها و نقش‌ها» (`/api/owner/accounts`) یکی نیست: نقش فقط از مسیر مالک تغییر می‌کند. در هیچ پاسخی شماره، digest، هش گذرواژه یا توکن برنمی‌گردد؛ ایمیل و نام کاربری مدیر فقط در نشست مالک.
- **حضور و غیاب** در پنل وب همان سیگنال مشترکی است که ربات هنگام اسکن بلیت می‌نویسد: ستون‌های `form_responses.ticket_checked_in_at` و `ticket_checked_in_by` (شناسهٔ بله). migration `0027` فقط ستون پوچ‌پذیر `ticket_checked_in_by_account_id` را برای عامل وب اضافه می‌کند و قابل بازگشت است. قاعدهٔ پرداخت همان قاعدهٔ ربات است (بدون تأیید پرداخت، حضور ثبت نمی‌شود)؛ برگرداندن حضور دلیل می‌خواهد و در `admin_audit_events` ثبت می‌شود. جلسه‌بندی و سوابق حضور رویدادهای قدیمی ربات (`attendance_sessions` در SQLite ربات) به پایگاه مشترک منتقل نشده‌اند و پنل وب آن‌ها را نشان نمی‌دهد.
- **گواهینامه‌ها**: منبع صدور همچنان SQLite ربات است (`certificates`، `cert_issues`، `cert_batches`)؛ از migration `0028_certificates` سرور یک **آینهٔ خواندنی** دارد که ربات پس از صدور/ابطال از طریق `POST /api/bot/certificates` پر می‌کند (فقط رکوردهایی که `bale_user_id` آن‌ها در `platform_identities` سرور باشد؛ بقیه جدا می‌مانند). گواهی‌های قدیمی فقط با `migrate_legacy_certificates.py` (پیش‌فرض dry-run، `--apply --yes`) و با تصمیم صریح منتقل می‌شوند.
- **باشگاه** هنوز فقط در SQLite ربات است (`users.total_points`، `achievements`، `user_achievements`، `rewards`، `reward_redemptions`، `greeting_log`). پنل وب تا تصمیم محصول (دفترکل امتیاز و تعریف سطح) فقط محدودیت را اعلام می‌کند و هیچ رکوردی را نمی‌سازد، منتقل یا حذف نمی‌کند.
