# راهنمای آزمون staging و دسترس‌پذیری فرم‌ساز نورا

## وضعیت این بازبینی

این سند وضعیت راستی‌آزمایی محلی را از آزمون پذیرش staging و آمادگی production جدا می‌کند. در بازبینی ۹ اکتبر ۲۰۲۶، smoke آفلاین با **۷۵۸ بررسی موفق و صفر خطا** اجرا شد. آزمون قرارداد قابلیت‌ها **۴ مورد موفق** داشت؛ گزینش آزمون‌های API شرط‌ها، readiness و موانع انتشار نیز **۴ مورد موفق و ۳۲ مورد کنارگذاشته‌شده** داشت. یک هشدار deprecation از `starlette.testclient` دیده شد.

آزمون کامل backend پس از تنظیم مسیر import نیز **۹۹ مورد موفق و صفر خطا** داشت؛ در آن هم یک هشدار deprecation از `starlette.testclient` ثبت شد. نتایج از JSDOM، mock API و SQLite موقت به‌دست آمده‌اند؛ **آزمون مرورگر واقعی روی میزبان staging یا PostgreSQL انجام نشده** و هیچ ادعای آمادگی production وجود ندارد.

## مرز قابلیت‌ها در رابط و سرور

`GET /api/public/forms/capabilities` قرارداد توصیفیِ عمومی و بدون راز را می‌دهد؛ سرور هنگام ذخیرهٔ تعریف، ثبت پاسخ و انتشار همچنان مرجع اعتبارسنجی است. `GET /api/forms/{id}/readiness` با مجوز فرم، مانع‌ها و نسخهٔ فعلی را از همان سرور می‌خواند و نباید وضعیت فرم را تغییر دهد. انتشار و توقف به اقدام صریح مالک، نشست معتبر، CSRF و نسخهٔ مورد انتظار نیاز دارند.

| قابلیت | وضعیت فعلی برای تجربهٔ staging |
| --- | --- |
| پاسخ عمومی ثبت‌نام، ظرفیت و صف انتظار | سروری؛ ظرفیت/صف در backend اعمال می‌شوند. ارتقای خودکار صف ادعا نمی‌شود. |
| شرط نمایش | سروری؛ حداکثر ۱۰ قاعده برای پرسش، ارجاع فقط به پرسش قبلی؛ backend ترتیب، عملگر، مقدار و گزینه‌ها را دوباره اعتبارسنجی می‌کند. |
| همراهان و مدل بلیت | مشروط به مدل ثبت‌نام و اعتبارسنجی backend؛ صف انتظار بلیت نمی‌گیرد. |
| فهرست پاسخ‌ها | فقط endpoint سروریِ مجاز؛ رابط ۵۰ پاسخ در هر صفحه می‌گیرد و شمار کل را از API می‌خواند. سقف endpoint طبق قرارداد ۱۰۰ است. |
| گزارش‌های کل و فرم | فقط شمار و وضعیت‌هایی که endpoint واقعی برمی‌گرداند؛ دادهٔ مرورگر با برچسب «نمونه» جداست و در جدول/آمار پاسخ سرور ادغام نمی‌شود. |
| پیش‌نمایش محلی | مصنوعی و جدا از draft/انتشار سرور است؛ ارسال واقعی پاسخ، پرداخت یا پیام ایجاد نمی‌کند. هیچ مقدار پروفایل خودکار وارد نمی‌شود. کمک پروفایل محلی فقط پس از اقدام صریح کاربر نمایش داده می‌شود. |
| فایل، رسانهٔ پرسش، احراز شماره/هویت، پیش‌پرکردن پروفایل عمومی | در قرارداد عمومی پشتیبانی نمی‌شوند؛ نباید در فرم منتشرشده به شکل قابلیت زنده عرضه شوند. پرچم قدیمیِ احراز شماره باید پاک‌سازی شود تا readiness مانع انتشار نماند. |
| محدودیت رویداد/حضور/دعوت، یک پاسخ برای هر شخص و زمان‌بندی انتشار | در backend فعلی پشتیبانی نمی‌شوند؛ کنترل فعال ندارند و دادهٔ قدیمیِ ناسازگار باید مانع انتشار بماند تا اصلاح شود. |
| سفارش و کیف پول بله | سفارش قابل انتشار نیست؛ کیف پول فقط با پیکربندی امن backend آماده می‌شود. آزمون staging در این راهنما هیچ پرداخت زنده‌ای انجام نمی‌دهد. کارت‌به‌کارت هم فقط با کارت معتبر، رسید و بازبینی دستی در مسیر مجاز قابل بررسی است. |

چهار قدم کاربرمحور سازنده ثابت می‌ماند: **مدل و نام، فیلدها و تنظیمات، مالی و پرداخت، مرور و ذخیرهٔ پیش‌نویس**. شش فاز، ترتیب توسعه است و به wizard قدم تازه‌ای اضافه نمی‌کند.

## اجرای آزمون‌های محلی

وابستگی‌های JavaScript را از فایل lock موجود در workspace نصب کنید؛ نصب وابستگی دادهٔ فرم یا پاسخ کاربر را ارسال نمی‌کند:

```bash
npm ci --ignore-scripts --no-audit --no-fund
NODE_OPTIONS=--max-old-space-size=3072 node docs/fa/nora-ui/smoke.test.mjs
```

برای آزمون backend، محیط مجزا بسازید و تست را با SQLite موقت اجرا کنید:

```bash
python3 -m venv /tmp/nora-backend-venv
/tmp/nora-backend-venv/bin/python -m pip install -r docs/fa/nora-ui/backend/requirements-dev.txt
/tmp/nora-backend-venv/bin/python -m pytest -q docs/fa/nora-ui/backend/tests/test_form_capabilities.py
/tmp/nora-backend-venv/bin/python -m pytest -q docs/fa/nora-ui/backend/tests/test_forms_api.py -k 'condition or readiness or publication_refuses'
PYTHONPATH=docs/fa/nora-ui /tmp/nora-backend-venv/bin/python -m pytest -q docs/fa/nora-ui/backend/tests
```

smoke مرورگر JSDOM است: HTTPS بیرونی را مسدود می‌کند، API را با mock هم‌مبدأ پاسخ می‌دهد و برای فرم‌های سروری درخواست‌ها را ثبت/assert می‌کند. آزمون backend نیز پایگاه‌دادهٔ درون‌حافظه‌ای می‌سازد. این روش‌ها جای آزمون اتصال staging واقعی یا استفادهٔ مجاز از مرورگر واقعی را نمی‌گیرند.

## چک‌لیست staging ایزوله

### پیش‌نیازها و مرز داده

- از hostname و پایگاه‌دادهٔ **جدا از production** استفاده کنید؛ پیش از migration، backup آزمایشی و روش بازگشت را ثبت کنید.
- فقط حساب‌های آزمایشیِ دارای مجوز کمینه و داده‌های ساختگی استفاده شوند؛ پاسخ، شماره، ایمیل یا اطلاعات پروفایل واقعی را در آزمون وارد نکنید.
- کلید، رمز و توکن فقط در secret store میزبان staging باشند؛ در HTML، query string، localStorage، log یا mock قرار نگیرند.
- provider پرداخت، SMS، ایمیل، اعلان و تحویل بات را به sandbox/سوییچ خاموش محدود کنید. تا وقتی آزمون صریح و مجاز دیگری تعریف نشده، هیچ پرداخت، ثبت‌نام واقعی یا پیام بیرونی نسازید.

### مسیر رابط و API

1. capabilityها را از همان origin بخوانید؛ نبود/خطای پاسخ نباید با یک مقدار پیش‌فرض به «آمادهٔ انتشار» تبدیل شود.
2. یک فرم ساختگی بسازید و پیش‌نویس ذخیره کنید؛ status و version را از API تازه بخوانید. صرف دیدن دکمه یا موفقیت محلی را ذخیرهٔ سروری فرض نکنید.
3. برای فرم دارای مانع، readiness باید کد/پیام مانع را نشان دهد؛ درخواست publish نباید ارسال شود و status/version نباید عوض شوند.
4. با مالک staging و CSRF معتبر، انتشار صریح را امتحان کنید؛ دوباره با نشست غیرمالک/منقضی‌شده، نسخهٔ قدیمی و فرم متوقف‌شده بررسی کنید که سرور انتشار/ویرایش را رد کند.
5. با دو یا چند پاسخ مصنوعی، پاسخ اصلی و همراه، `limit=50` و `offset`های بعدی را بررسی کنید؛ هر صفحه باید از endpoint واقعی باشد. مجموع گزارش باید با `total` همان endpoint سازگار باشد و نمونه‌های محلی در آن جمع نشوند.
6. مسیر preview را جداگانه باز کنید: باید برچسب پیش‌نمایش داشته باشد، فرم از پاسخ قبلی پر نشود و هیچ POST ثبت پاسخ، پرداخت، پیام یا انتشار رخ ندهد.
7. آزمون فایل/تأیید شماره/احراز، زمان‌بندی، محدودیت هویتی و سفارش را به‌صورت negative انجام دهید: UI علت پشتیبانی‌نشدن را بگوید و backend نیز انتشار را متوقف کند؛ این آزمون به معنی پیاده‌سازی قابلیت نیست.

برای هر اجرا، تاریخ، commit، نسخهٔ schema/migration، hostname محیط (بدون credential)، نتیجهٔ هر مرحله، کد مانع، و log پاک‌سازی‌شده ثبت شود. log نباید پاسخ یا اطلاعات شخصی داشته باشد.

## بازبینی دسترس‌پذیری با صفحه‌کلید و صفحه‌خوان

آزمون خودکار فعلی، نام دسترس‌پذیر دکمه‌ها، مرزهای غیرفعال بالا/پایین، کلیدهای میانبر، حفظ فوکوس پس از مرتب‌سازی صفحه‌کلیدی و drag-and-drop، `aria-posinset`/`aria-setsize`، پیام زندهٔ جابه‌جایی و برخی حالت‌های خطای فرم را در DOM بررسی می‌کند. این‌ها به‌تنهایی تأیید WCAG یا تجربهٔ صفحه‌خوان نیستند؛ موارد زیر در staging باید دستی اجرا و نتیجه ثبت شوند:

- همهٔ قدم‌ها، کاتالوگ، sheetها، شرط‌ها، کنترل‌های انتخاب و دکمه‌های پایین/بالا را فقط با Tab، Shift+Tab، Enter، Space و کلیدهای جهت‌دار طی کنید؛ فوکوس گم یا در sheet گیر نکند.
- ترتیب پرسش را با دکمه‌های صفحه‌کلیدی بالا/پایین تغییر دهید و سپس با drag-and-drop امتحان کنید. هر دو روش باید به همان ترتیب مدل منتهی شوند؛ drag روش یگانه نباشد. پیام `aria-live` جایگاه تازه را اعلام کند و بعد از جابه‌جایی فوکوس قابل پیش‌بینی بماند.
- با NVDA/Firefox و VoiceOver/Safari، نام پرسش، اجباری‌بودن، وضعیت کلیدها، علت غیرفعال‌بودن قابلیت، شرط نمایش و پیام‌های خطا را بخوانید. برچسب‌های فارسی/انگلیسی/عددها نباید فقط با رنگ یا آیکن فهمیده شوند.
- فیلد اجباری خالی را ارسال کنید: خطا باید متن روشن داشته باشد، `aria-invalid`/`aria-describedby` به پیام وصل باشند و فوکوس به کنترل نیازمند اصلاح برسد. پس از اصلاح، وضعیت نامعتبر و پیام stale نمانند.
- در zoom مرورگر ۲۰۰٪ و ۴۰۰٪ و viewport باریک، RTL و LTR را بررسی کنید؛ متن، منو، شمارنده، دکمهٔ ثبت و صفحه‌بندی نباید روی هم بیفتند یا نیازمند پیمایش افقیِ صفحه باشند.
- حالت کنتراست بالا/forced colors و `prefers-reduced-motion` را بررسی کنید؛ نشانگر فوکوس، وضعیت خطا و وضعیت انتشار باید بدون انیمیشن یا رنگ تنها قابل تشخیص باشد.
- پروفایل واقعی را در فرم preview قرار ندهید. ابتدا با انبار خالی بررسی کنید ورودی‌ها خالی‌اند؛ اگر پیش‌نمایش محلی کمک پروفایل دارد، تنها پس از کلیک صریح کاربر مقدار ساختگی مجاز را بررسی کنید.

## کارهای باز پیش از پذیرش staging/production

- آزمون این نوبت فقط JSDOM و SQLite بوده است؛ PostgreSQL واقعی، migration staging، TLS، reverse proxy، cookie `Secure`/`SameSite`، origin/CSRF در دامنهٔ واقعی و backup/restore بررسی نشده‌اند.
- آزمون دستی واقعی صفحه‌خوان، contrast، zoom و موبایل هنوز انجام/امضا نشده است؛ فهرست بالا معیار اجرای بعدی است، نه گزارش قبولی.
- هیچ پرداخت، ارسال پیام/ایمیل/SMS، تطبیق هویت، بررسی پاسخ‌دهندهٔ واقعی یا readiness میزبان production در این نوبت انجام نشده است.
- تا ثبت نتیجهٔ موارد بالا، محصول **برای production تأییدشده نیست**.
